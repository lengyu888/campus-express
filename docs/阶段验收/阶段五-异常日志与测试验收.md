**异常闭环**

```text
登记异常（包裹 → exception）→ open 待处理 → processing 处理中 → resolved 已解决
                                                          ├─ restock  重新入库（保留格口）
                                                          ├─ returned 退回发件方（释放格口）
                                                          └─ keep     保持异常
```

**后端接口（5 个 + 审计中间件）**

| 方法 | 路径 | 说明 | 权限 |
| --- | --- | --- | --- |
| GET | `/exceptions` | 异常列表（状态、类型、驿站、关键字） | 工作人员、管理员 |
| GET | `/exceptions/summary` | 待处理 / 处理中 / 已解决统计 | 工作人员、管理员 |
| PATCH | `/exceptions/{id}` | 处理异常（状态 + 包裹处置） | 工作人员、管理员 |
| GET | `/logs` | 操作日志分页与筛选 | 管理员 |
| GET | `/logs/summary` | 日志总数、今日数、模块分布 | 管理员 |

审计中间件：所有成功的 `POST / PUT / PATCH / DELETE` 自动落库，失败请求不记录；模块与动作由路径解析（如 `POST /packages/{id}/pickup` → 包裹 / 取件出库），只记录路径、方法、状态码，**不记录请求体**，避免密码等敏感信息入库。

**业务规则**

1. 同一包裹同时只能存在一条未处理异常（`open` / `processing`）。
2. 仅 `in_stock` / `overdue` 状态可登记异常，登记后包裹置为 `exception`。
3. 状态只能向前流转，`resolved` 后不可重复处理。
4. 解决时选择「重新入库」保留原格口；「退回发件方」释放格口并清空取件码；「保持异常」仅关闭异常记录。
5. 异常解决后向收件人推送站内通知。
6. 操作日志只记录成功请求，避免失败重试污染审计数据。

- **异常处理**：四张指标卡、状态分段控件、类型筛选、关键字搜索、异常卡片（运单、类型、驿站货架、描述、收件人、处理人）、处理弹窗（状态 + 包裹处置 + 处理说明）

## 四、已知限制

1. 操作日志只记录请求元信息，未保存字段级变更前后的值。
2. 异常件「重新入库」要求包裹仍保留格口，已释放格口的包裹需先调架。
3. 超期状态为读取时实时计算，没有定时任务批量刷新，也没有自动退回。
4. 日志未做归档与清理策略，长期运行需要按时间分区或定期归档。
5. 测试用例为手工 + 接口脚本执行，未接入自动化测试框架（pytest / Playwright）。
